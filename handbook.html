Optional implementation reference

Keep the principles.
Choose tools that fit your team.

An owned source, a reviewable draft, an explicit decision and a retrievable record work across many stacks. The repo and command-line approach below is one implementation.

Principles to carry over

  • Name the source and the person accountable for it.
  • Let AI draft work people can inspect.
  • Separate structural validation from factual review.
  • Record the decision and the reason for it.

Choose by the work

A Git repository can fit teams comfortable with branches and reviews. A maintained document store or existing work system may fit others better.

Choose after checking access, versioning, sensitive data, integrations and who will maintain it.

One repo implementation: four connected layers

Illustrative architecture. A source repository, Markdown records, YAML metadata and Git reviews provide a concrete pattern. These layers do not certify a current deployed product or require moving all company data into one place.

01

Source vault

Owned records with dates, permissions and version history: process notes, decisions and approved material.

↓ The schema describes those records.

02

Schema

Required fields for identity, source, owner and state. A validator checks structure; a person checks meaning.

↓ Agents read authorised sources and produce structured drafts.

03

Agent tasks

Bounded instructions and tools for extraction, drafting or critique, with a named reviewer and a stop condition.

↓ Retrieval can find related evidence as the source set grows.

04

Graph + memory

Search, links and summaries point back to source records. Source changes require index and memory maintenance.

Keep access controls in the source and retrieval paths. A graph link shows a relationship to inspect; it doesn't establish that a claim is true. Read the memory reference →

Engineer and process-owner working paths

For an engineer

  1. Read the task, source records and acceptance checks.
  2. Create an isolated branch and make the scoped change.
  3. Run relevant tests and inspect the complete diff.
  4. Ask the reviewer to accept the change before merging or releasing.

For a process owner

  1. Bring a real job and the sources you trust.
  2. Ask for a draft with links to those sources.
  3. Resolve missing facts and check the result.
  4. Approve the next action and record the decision.
Example instruction

“Draft a reply using the approved policy. Cite the paragraph for each policy claim. List questions you can't resolve. Wait for my approval before sending.”

Use an interface the team can operate. Terminal access is an implementation choice, not a prerequisite for useful work.

Make changes reviewable and decisions durable

Branches and reviews

Keep one bounded change on a branch. Give the reviewer the problem, changed behaviour, evidence and remaining limits. Review generated files as carefully as handwritten work.

A schema check can reject missing fields. A human still checks source fidelity, scope and permission to act. Merge and release remain separate decisions where the team requires them.

Decisions and journals

Record who decided, what changed, why and which evidence they used. Link the entry to the source and resulting work.

At the end of a work session, record completed work, unresolved questions and the next owner. Keep chat useful for discussion and move lasting decisions into the agreed record.

Catch the failure modes before expanding

  • Unowned sources

    Name who updates each source and how the team spots stale or contradictory material.

  • Valid format, wrong content

    Test source fidelity and business meaning separately from required fields.

  • One operator knows it all

    Have another person run the documented checks and fallback.

  • Infrastructure before use

    Start with one job the team will repeat. Add machinery when observed work justifies it.

  • No place for uncertainty

    Let a draft say unknown and return the question to its owner.

  • Expansion without evidence

    Review the baseline, results and operating load before adding another workflow.

Sequence the rollout by demonstrated readiness and dependencies. Calendar milestones belong in the agreed project plan.
