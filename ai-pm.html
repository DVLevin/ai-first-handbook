Approve the proposal before generating files.

  1. Read the source

    Use the transcript or approved notes. Preserve the source reference with each extracted decision.

  2. Propose the work

    Draft tickets and surface missing information. An unknown owner stays unknown.

  3. A person approves the proposal

    The product owner changes, rejects or accepts the proposed work before files are generated.

  4. Generate draft files

    Write the approved structure without committing. Generated files are still drafts.

  5. A person reviews and chooses to commit

    Check the files against the source, edit them and decide whether to make a commit.

  6. Validate at the commit attempt

    The mechanical schema check permits valid structure. Invalid structure returns to editing. A valid schema does not prove a fact is right.

Start where a person can judge the result.

A good first process has recurring source material, a person who can judge the work, and a clear place for accepted tickets. Start where preparing a draft is useful and the review can be explicit.

Bring real examples

For a later scoped evaluation, select representative source notes and the tickets your team accepted. Include ambiguity, contradictory decisions and changes of direction.

Name the decision owner

The product owner retains scope and priority. A workflow operator checks failed runs and routes questions. Agree who maintains the integration and how to stop it.

The free plan needs only the process, current tools or agents and the bottleneck. Private source material and systems access belong to a separately agreed evaluation.

How to operate the workflow.

Source fidelity and open questions

Store a source identifier with the extracted decision. A paraphrase must preserve the original commitment. Separate a suggestion from an accepted decision. If a person, date or scope is absent, keep an open question instead of filling the gap.

A reviewer should be able to move from a draft field to the exact supporting passage. Conflicting passages need a human decision, not an apparently certain summary.

Generation, version control and schema checks

The proposal approval and the file review are separate gates. Generating files does not authorise a commit. At commit time, a mechanical validator can enforce required keys, field types and identifiers. It cannot confirm business priority or source truth.

Keep the previous accepted version so a bad change can be reverted. The integration's permissions should match the authorised action; avoid giving a drafting step permission to publish or send.

Evaluation that reflects the work

Use a dated, versioned sample with a human reference. Report the number of source decisions and accepted tickets separately. Record missing decisions, unsupported additions, reviewer edits and review time. A small internal sample supports a narrow conclusion.

Model-call cost is one cost component. Include setup, review, maintenance and exception handling when assessing whether this workflow helps.

Operating the queue

Keep a record of the source, draft, human decision, validator result and accepted output. When a check fails, stop the affected action and route the record to its owner. Diagnose repeat failures before expanding the workflow.

Data access, storage, retention and tool licences depend on the selected implementation and agreement. Your records and the software used to process them are distinct parts of that decision.
